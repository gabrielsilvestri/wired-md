# wired-md

Editor de markdown desktop em Electron, estilo Typora (WYSIWYG live, sem split view), feito para quem escreve markdown para IA (CLAUDE.md, skills, prompts, notas de agente).

## Objetivo

- Editar .md com renderização inline ao estilo Typora (o markdown "vira" o documento enquanto digita).
- Visual idêntico ao dashboard da lain (`.lain/dashboard/index.html`): fundo #101216, tinta #bcc2c9, accent teal #4fc7bb, JetBrains Mono, bordas sussurro.
- Customização estilo Obsidian: temas custom (arquivos de tema), troca de fonte, cor de accent, CSS snippets que o usuário liga e desliga.
- Terminal simples embutido (painel inferior) para invocar `claude` no diretório do arquivo aberto.

## O que mede sucesso

Abrir um .md real, editar com preview inline, trocar tema/accent/fonte ao vivo, ligar um snippet de CSS, abrir o terminal e rodar `claude`. Tudo sem crash no Windows 11.

## Como rodar

```
npm install
npm start
```

## Customização (fase 2, implementada)

- Temas: arquivos .css em `%APPDATA%\wired-md\themes\` que definem só as CSS variables (`:root { --bg: ...; }`). Os padrões `wired` (dark) e `claro` são copiados de `themes/` do repo no primeiro boot. Seletor no painel de configurações (engrenagem).
- Snippets: .css em `%APPDATA%\wired-md\snippets\`, ligados um a um por toggle no painel; aplicados por cima do tema.
- Accent, fonte do documento, fonte de código e tamanho do texto: overrides no painel; accent deriva soft/ink/dim por mistura com branco/preto no renderer.
- Tudo persiste em `%APPDATA%\wired-md\config.json` (theme, accent, fontBody, fontCode, fontSize, snippets) e é aplicado no boot.
- Terminal embutido: Ctrl+` (painel inferior, xterm.js). Backend node-pty rodando; fallback de pipes existe em `startPipeShell` no main.js caso o binário quebre. Botão claude digita o comando no shell.
- Smoke test sem interação: `WIRED_SMOKE=1 npm start` (loga backend do terminal, buffer do xterm, config e temas, e sai sozinho).
- Teste ponta a ponta (fase 3): `WIRED_E2E=1 npx electron . exemplos/demo.md` dirige o renderer de verdade (teclado real via sendInputEvent, Ctrl+S, troca de tema, accent, snippet, terminal com dir) e imprime PASS/FAIL por fluxo; exit code 0 só com tudo verde. Salva screenshot em docs/screenshot.png e restaura o demo.md ao final.
- Atalhos globais do renderer ficam em listener de keydown na FASE DE CAPTURA: o Vditor consome keydown dentro do editor, então sem captura o Ctrl+S digitando no texto não chega ao handler.

## Busca full-text na pasta (fase 7, implementada)

- Ctrl+Shift+F abre um overlay na mesma família visual da palette (mesmo fundo, borda, raio, animação e linha accent do item selecionado) e busca por CONTEÚDO nos .md/.markdown da pasta da nota aberta. O quick switcher (Ctrl+P) segue sendo busca por NOME; esta é a resposta pra "onde foi que eu escrevi aquela regra". Também tem ação na palette: "buscar na pasta".
- Motor: o binário do ripgrep que vem no npm `@vscode/ripgrep` (offline, ~5,2 MB no node_modules por causa do subpacote `@vscode/ripgrep-win32-x64`). O pacote é ESM e o main.js é CJS, então o binário é resolvido direto no subpacote da plataforma (`require.resolve('@vscode/ripgrep-' + process.platform + '-' + process.arch + '/bin/rg.exe')`), sem importar o wrapper. Sem o binário, o handler cai num scan recursivo em Node puro com a mesma poda de pastas do file tree. `WIRED_SEARCH_ENGINE=node` força o fallback (as duas rodadas do E2E, com rg e sem, ficam verdes).
- IPC `search:folder` (root, query): busca literal (`--fixed-strings`), smart case, `--no-ignore` (senão .gitignore esconderia nota) e globs que repetem a régua do file tree (só .md/.markdown, fora node_modules, .git, .obsidian, .trash; oculto o rg já pula sozinho). Teto de 200 matches, com `truncated` indo pro status. Grupos ordenados por caminho: o rg varre em paralelo e a ordem dele muda a cada busca.
- Offset do rg vem em BYTES dentro da linha; a UI mostra caractere. A conversão é `Buffer.slice(0, byte).toString('utf8').length`, senão qualquer linha com acento desalinha o destaque. Linha longa é recortada numa janela de 240 caracteres em volta do match.
- UI: mínimo de 2 caracteres, debounce de 200ms, resposta fora de ordem descartada por número de sequência. Resultados agrupados por arquivo (nome + contagem), cada linha com número e o trecho destacado (`.search-hit`, tinta da família accent via `--search-hit-ink` sobre o accent a 0.18 composto na linha; medido de 5,23:1 a 6,47:1 nos dois temas, dentro da faixa 4.5:1 a 11:1; o valor do tema claro foi corrigido, antes furava o piso). Setas andam por TODOS os matches (a lista achatada `searchHits`), Enter abre no pane ativo, Ctrl+Enter abre ao lado, Esc fecha.
- LIMITE DO PULO ATÉ O TRECHO: o Vditor IR é WYSIWYG, não existe "ir pra linha N". O `jumpToText` procura o texto do match no DOM renderizado do pane, seleciona e rola até ele; quando o trecho virou marcação (linha de tabela, link, cerca de código) ele não é achado e o arquivo só abre no topo, sem erro. É melhor esforço declarado, não bug.
- E2E da fase 7: 40 checks no total (5 novos). Cobrem Ctrl+Shift+F de verdade (sendInputEvent) abrindo o overlay com foco no campo, a query achando o termo em dois arquivos fixture com a contagem certa, o destaque do trecho, setas + Enter abrindo o arquivo do match selecionado e Esc fechando com a ação na palette.
- ARMADILHA GRANDE (custou a fase inteira): quando a janela do app fica COBERTA por outra (o terminal que dispara o teste), o Chromium marca a janela como ocluída no Windows e PARA de renderizar. Aí `window.innerWidth` congela na largura do maximizado, `mainWindow.setSize` não mexe mais no viewport e transição de CSS não avança (o pane colapsado fica com o `flex` do início da animação). Isso derrubou os 3 checks de lombada/resize sem ninguém ter tocado neles. Correção: nos modos de teste, `app.commandLine.appendSwitch('disable-features', 'CalculateNativeWinOcclusion')`. Em uso normal a detecção continua ligada. Sintoma pra reconhecer de novo: medida de layout que não bate com o bounds da janela.

## Frontmatter como painel de propriedades (fase 8, implementada)

- Arquivo que começa com bloco YAML entre `---` ganha um PAINEL DE PROPRIEDADES no topo do pane (entre o cabeçalho e o editor, um por pane porque cada pane é um arquivo). Cada chave vira uma linha: texto para string e número, campo com itens separados por vírgula para lista (`tools`), checkbox para booleano, e caixa tracejada de leitura para o que o painel não representa (mapa aninhado, lista de mapas), que fica intocada no arquivo. Chave não se renomeia pelo painel na v1, só o valor.
- DECISÃO DE RENDERIZAÇÃO: vista dupla sincronizada, não bloco escondido. O Vditor IR já trata frontmatter como nó próprio (`div.vditor-ir__node[data-type="yaml-front-matter"]`, com `pre > code.language-yaml` dentro) e faz round trip exato dele, então esconder por CSS seria fácil; foi descartado porque o nó é contenteditable: com `display:none` o cursor ainda entra nele por Ctrl+Home, seta pra cima ou Ctrl+A e a pessoa digitaria no escuro, sem ver o que edita. Então o bloco continua visível no documento e o painel é a vista estruturada em cima dele, com sincronização nos dois sentidos.
- SINCRONIZAÇÃO: editar no painel reescreve o bloco no documento (`fmCommit`, no evento `change` do campo, ou seja no blur e no Enter) e marca o pane sujo igual a digitar; Ctrl+S grava frontmatter reescrito + corpo. Editar o bloco na mão dentro do editor refaz o painel com debounce de 450ms (`scheduleFmRefresh`, pendurado no callback `input` do Vditor). Duas travas contra laço: `pane.fmQuiet` ignora o refresh disparado pelo próprio `setValue` do commit, e o refresh não redesenha as linhas enquanto o foco está dentro do painel.
- PARSER: `yaml` do npm (~1 MB no node_modules), rodando no PRELOAD, não no renderer nem no main. No renderer não dá (contextIsolation, sem require) e no main viraria round trip de IPC a cada edição; o preload tem require e o contextBridge só deixa passar objeto simples, então o `Document` do yaml nunca sai de lá. A ponte expõe duas funções: `fmParse(raw)` (entradas classificadas) e `fmSet(raw, key, kind, value)` (escreve uma chave e devolve o YAML re-emitido).
- ROUND TRIP: o bloco só é reescrito quando alguém edita uma propriedade; nesse caso ele é re-emitido inteiro pelo serializador do `yaml` a partir do Document original, o que preserva ordem das chaves, comentários, chaves desconhecidas, mapas aninhados e o estilo de bloco das listas. O que pode normalizar é formatação exótica (indentação fora do padrão, aspas desnecessárias, YAML em flow). Enquanto ninguém mexe no painel, o arquivo não é tocado.
- SCHEMAS (escolhidos sozinhos): `skill` quando o arquivo se chama SKILL.md; `subagent` quando ele está numa pasta chamada `agents` ou quando tem `name` junto de `tools`/`model`; `generico` no resto. Skill e subagent exigem `name` (kebab-case) e `description` não vazia, avisam sobre `tools` que não é lista nem texto com vírgula e sobre `model` fora de sonnet/opus/haiku/inherit (aviso leve), e apontam chave parecida como typo provável (`Name`, `describe`, `desc`, `Tools`, `modelo`...). Genérico só valida se o YAML é válido.
- Os avisos saem como linha compacta dentro do painel (ícone de alerta + frase curta em pt-BR, tinta de aviso da família âmbar via `--warn-ink` sobre o `--bg-2`: 7,78:1 no wired e 5,19:1 no claro, dentro da faixa 4.5:1 a 11:1; o `--amber` da bolinha de não salvo continua intocado, e o valor do claro foi corrigido porque o `--amber` cru furava o piso ali). Nunca popup, nunca bloqueia digitar ou salvar. YAML inválido derruba o painel pra leitura crua (`pre.fm-raw` com o bloco) e mostra o erro do parser.
- TOGGLE: ação "propriedades: mostrar/ocultar" na palette, com `frontmatterPanel` (padrão true) no config.json.
- E2E da fase 8: 46 checks no total (6 novos). Cobrem painel aparecendo no arquivo com frontmatter (lista, booleano e mapa preservado nas linhas certas) e sumindo no arquivo sem, edição marcando sujo e Ctrl+S gravando em disco, round trip com mapa aninhado e comentário intactos, schema skill acusando `description` faltando e `describe` como typo, YAML inválido caindo em leitura crua sem campos editáveis, e o toggle da palette ocultando o painel e persistindo no config.json. O fixture é `exemplos\exemplo-skill.md` (versionado); o teste guarda o conteúdo original e reescreve no fim, como já fazia com o demo.md.
- Armadilha achada: o `lute` come a linha em branco entre o `---` de fechamento e o corpo (o `getValue` volta sem ela). Não é do painel, é normalização do Vditor, mas significa que abrir e salvar um arquivo que tinha essa linha muda um byte. O fixture nasceu sem a linha em branco pra o teste não medir esse ruído.
- Limite conhecido: a régua de frontmatter é "arquivo começa com `---`". Documento que abre com uma régua horizontal `---` e tem outra `---` adiante seria lido como frontmatter, igual ao resto do ecossistema markdown.

## Novo arquivo a partir de template (fase 9, implementada)

- TEMPLATES são .md em `%APPDATA%\wired-md\templates\`, semeados do `templates\` do repo no primeiro boot, no mesmo `ensureUserDirs` que semeia temas e snippets (a régua de extensão virou parâmetro do par origem/destino: .css pra tema e snippet, .md pra template). - VARIÁVEIS: `{{data}}` (AAAA-MM-DD), `{{hora}}` (HH:mm), `{{titulo}}` (nome do arquivo sem extensão), `{{pasta}}` (nome da pasta de destino), `{{cursor}}` (onde o caret pousa depois de criar; o marcador some do arquivo) e `{{pergunta:label}}` (pergunta ao usuário no dialog do próprio app, na ordem de aparição). O mesmo label é perguntado UMA vez e substituído em todas as ocorrências. Marcador `{{...}}` desconhecido fica intacto, nunca vira erro. Resposta que preenche o VALOR INTEIRO de uma chave dentro do frontmatter YAML vira escalar entre aspas duplas com escape (`valorInteiroDeChaveYaml` + `yamlEscalarAspas`), então aspas, dois-pontos e `#` na resposta não quebram o YAML nem fazem o arquivo recém-criado abrir com "YAML inválido"; por isso os templates `skill.md` e `subagent.md` trazem `description: {{pergunta:...}}` SEM aspas na mão (a substituição é que cita).
- FLUXO: ação "novo a partir de template" na palette, botão na toolbar da sidebar (vizinho do novo .md) e item "novo a partir de template aqui" no menu de contexto de pasta. A ordem é: seletor de template (overlay `#template-overlay`, mesma família visual da palette, setas + Enter, Esc cancela) → dialog de nome (`#input-overlay`, o mesmo de criar e renomear) → as `{{pergunta:...}}` → criação. O alvo é a pasta selecionada na árvore ou a raiz da nota, a mesma régua do "novo .md"; sem pasta aberta o texto vai pro buffer sem título.
- CANCELAR não deixa lixo: o arquivo só é criado DEPOIS da última resposta, então Esc (ou campo vazio) em qualquer passo aborta sem tocar no disco. `skill.md` e `claude-md.md` sugerem `SKILL.md` e `CLAUDE.md` como nome; o resto sugere `sem-título.md`.
- A pasta de templates é RELIDA a cada abertura do seletor (`templates:list` no main), então template largado ali com o app aberto aparece sem reiniciar e sem watcher. Nada novo persiste no config.json.
- CARET no `{{cursor}}`: o arquivo é gravado já sem o marcador, e o editor recebe o conteúdo com um token invisível (o caractere de uso privado U+E000) no lugar; o token é achado no DOM renderizado, removido do nó de texto e o caret fica exatamente ali. Se o token não sobreviver ao render do lute, o conteúdo limpo é reposto e o caret fica no fim (melhor esforço declarado, igual ao pulo da busca).

No E2E, chamada de função async do renderer vai como `void f()`. Sintoma: o teste congela sem FAIL, com o app vivo e o arquivo já criado em disco.

## Cifrão é dinheiro, não fórmula (fase 11)
